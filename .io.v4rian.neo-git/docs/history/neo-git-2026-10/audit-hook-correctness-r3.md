## New findings

### R3-01 [MEDIUM] By-SHA and detached-HEAD requirement resolution regressed once a lane drops a stale file (R2-07 fix breaks R2-06 fix)
- `scripts/get-active-requirement.sh:125`: `git diff-tree --no-commit-id --name-only -r "$FIRST_REQ_SHA" -- "$HG_REQUIREMENTS_DIR" | head -1`. Since 66d5bc3 the `[REQ]` commit also deletes the inherited lane files, and `--name-only` lists them; the deleted `n1` path sorts before the added `n2` path, `git show` of it fails, and the code falls through to the scrubbed body.
- Evidence VERIFIED (scratch, off-grid, requirement "Requirement N - verbatim."): lane 1: by name / by SHA / detached all `Requirement 1 - verbatim.`; after merging lane 1 into dev, lane 2's `[REQ]` diff-tree is `D …n1… A …n2…`, by name `Requirement 2 - verbatim.`, by SHA and detached `Requirement 2, verbatim.`; same for lane 3. The R2-06 test allocates a single lane and the R2-07 test reads by name only, so neither sees it.
- Fix: `git diff-tree --no-commit-id --name-only --diff-filter=A -r …` (one flag), and read it at `$BRANCH`.
- Test: in `test_hc_r2_06_*` allocate and merge a first lane before the probed one, keep the by-SHA and detached assertions; or assert by SHA in `test_hc_r2_07_*`.

### R3-02 [MEDIUM] Migrated lanes that share one legacy blob conflict rename/rename on dev
- `scripts/migrate-active-requirement.sh:66-70`: each migration commit deletes `active-requirement` and adds the lane file with the same blob, which git's rename detection reads as a rename. Two lanes doing that from one common ancestor blob to two paths is a rename/rename(1to2) conflict at merge time, the exact failure the tool exists to remove.
- Evidence VERIFIED on the wallvee copy: n5 `pool/v2026.0/n5.feature.wallpaper-all-desktops-and-screens` was forked from n4's tip 64677a5 (`merge-base n5 n4` = 64677a5, n4 is an ancestor of n5), so both carry blob `933f311b`. After migrating both and landing n4 on dev, `git merge n5` → `CONFLICT (rename/rename): .io.v4rian.how-git/active-requirement renamed to …n4… in HEAD and to …n5… in pool/…n5…`, index `DD`/`AU`/`UA`. With `-X no-renames` the same merge lands and dev holds both lane files. The R2-02 test gives the two lanes different texts, so it cannot see this. Stacked lanes (a lane cut from another lane) and re-allocations of the same requirement text are the real-world shapes; 1 of the 2 consumers probed has one.
- Fix (pick one, both small): (a) `hg_legacy_requirement_lanes`/migrate: when a lane's legacy blob is also carried by another local lane (or by the lane it forked from), keep the legacy file in place and only add the lane file, so one side renames and the other leaves it unchanged (git then applies the rename cleanly and dev ends without the legacy file); (b) the claim and finalize merge tools resolve a rename/rename(1to2) whose source is exactly `HG_LEGACY_REQUIREMENT` by keeping both lane files and dropping the legacy path, and say so in the merge body. (a) needs no merge-tool change; (b) also heals hand merges through `post-merge`.
- Test: lane B cut from lane A's tip (both legacy, identical text); migrate both; land A then B on dev; dev ends with two lane files and no `active-requirement`.

### R3-03 [MEDIUM] A lane without a local `safety/` branch pushed to an empty destination re-judges its whole history: HC-04 re-opened for clone-shaped repos, 40 s on neo-git
- `githooks/pre-push:93-98`: the anchor is `refs/heads/safety/${name#pool/}` only. A clone brings `refs/remotes/origin/safety/*`, not local branches; some checkouts also lack them (`foundry.wa`: 17 pool, 13 local safety; `how-apple`: 50 local safety, 0 remote-tracking).
- Evidence VERIFIED on a clone of neo-git at local/hook-correctness (638 commits, one `--no-verify` "plus" commit on `pool/v2026.0/n99.fix.probe`): push by URL to an empty bare remote, no anchor: rc=1, **92 refusals** (91 legacy dev commits + the probe), wall 39.8 s (31.9 s user: one python3 per commit ≈ 62 ms); same with the anchor present only as `refs/remotes/origin/safety/v2026.0/n98.fix.probe`: rc=1, 82 refusals, 42.1 s; with a local `safety/…` at the fork point: 1 refusal, 0.15 s. The dev history itself has 91 of 586 commits that break today's rules (`hg_message_violations` over `git rev-list dev`), so any first push of a lane from such a repo to a mirror is refused for commits the pusher never wrote. The 51 branch commits are all clean.
- Fix: resolve the anchor from more than one place, in order: local `refs/heads/safety/<lane>`, then `refs/remotes/*/safety/<lane>`, then `git ls-remote <configured upstream of the lane, else origin> refs/heads/safety/<lane>` (one round trip, only on the empty-destination path); and judge the range in one python process (feed `git log --format='%H%x00%B%x00'` to a batch mode of `_HG_MSG_RULES_PY`) so a long range costs one interpreter start, which also closes the R2-05 class for good.
- Test: in `test_hc_hc04_*` replace the local safety branch by `refs/remotes/origin/safety/<lane>` and assert the by-URL push of the clean lane still passes.
